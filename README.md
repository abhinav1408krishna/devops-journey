## Learning Workflow

Each learning unit follows a repeatable workflow:

1. Review the learning objectives and relevant concepts.
2. Complete hands-on exercises and troubleshooting tasks.
3. Attempt a mini challenge without blindly following instructions.
4. Record useful notes, commands, results, and unresolved questions.
5. Update the Knowledge Book or other learning documentation when there is meaningful new knowledge.
6. Review the work and record progress honestly in the tracker.
7. Commit and push a coherent, reviewed batch of changes.
8. Review progress and plan the next learning unit.

### Repository Update Policy

Learning and repository maintenance are related, but they do not need to happen after every command or practice session.

- **During practice:** Keep local notes and capture useful results.
- **At meaningful milestones:** Update relevant lesson notes, scripts, project documentation, and tracker status.
- **In batches:** Review related changes together, validate them, and create a focused Git commit.
- **After review:** Push the approved batch to GitHub.
- **For incomplete work:** Record what remains; do not mark a lesson, lab, or project complete prematurely.

The goal is consistent, trustworthy documentation without unnecessary administrative overhead.

## Repository Standards

Learning records and projects should include the elements relevant to their scope.

### Lessons
- Learning objectives and prerequisites
- Key concepts and useful commands
- Hands-on exercises and observed results
- Troubleshooting notes and unresolved questions
- Reflection and a clear completion checklist

### Projects
- Problem statement, objectives, requirements, and architecture
- Beginner-friendly, step-by-step build instructions that do not assume prior DevOps or computer science experience
- Exact directory and file paths, setup commands, and section-by-section implementation guidance
- Explanations of important code, configuration, and component interactions
- Run instructions, verification commands, expected results, and tests
- Troubleshooting guidance and safe cleanup instructions
- Clear acceptance criteria and evidence supporting completion
- Challenges, lessons learned, and future improvements

Use [`Templates/project-template.md`](Templates/project-template.md) as the starting point for new project guides. Adapt it to the actual project and remove generic placeholders before considering the guide complete.

### Progress and Documentation
- Keep the tracker consistent with actual work.
- Update the Knowledge Book when there is useful knowledge to preserve.
- Keep project status and completion claims evidence-based.
- Use the templates in `Templates/` where appropriate.
- Batch related repository updates and review them before pushing.
